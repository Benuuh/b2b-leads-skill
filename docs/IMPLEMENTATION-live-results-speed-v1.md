## 2. 数据契约

页面只读取 `data/skill-v2/live/<run>/projection.json`（受管理工件目录内），不查询业务表以外的任何来源，也不触发 research、maintenance 或状态修改。

| 页面字段 | 来源定义 |
|---|---|
| 目标 | 冻结 `spec.quantity`，不随结果调整 |
| 已准入 | `plan.research.admitted_count`（原 `discovered` 语义，累计接收的去重前候选） |
| 已确认可交付 | `delivery_companies()` 的长度：同一交付选择、去重、抑制、渠道政策 |
| 待核实 | 同一选择中已确认合格但未达到可交付（缺渠道/证据过期/官网归属待确认），加上 `decision=uncertain` 的安全投影；不含 excluded |
| 剩余缺口 | `max(目标 − 已确认可交付, 0)` |
| 可导出 | `min(已确认可交付, 目标)`，与正式导出的行数一致 |
| 已发现 | 恒为 `null` + “暂不可得”；不把已准入或搜索次数冒充全网发现 |
| 状态 | 提交时读到的真实 `run.status`；`circuit_open` 显示失败/受阻；超过 120 秒未观察到更新的 running 显示“未知” |
| 时间 | `generated_at` 为本次投影生成时间；`run.observed_at` 为最近一次已提交状态变更时间；两者分别展示 |

投影带 `revision`（数据修订，不含生成时间和运行秒表）与 `companies_signature`（企业行数 + 最近更新时间）。相同签名可复用已保存页面或提交时缓存的选择结果，避免重复执行最昂贵的交付选择。

写入规则：

- 临时文件 + `os.replace` 原子替换；异常时保留上一份完整页面并清理临时文件。
- 数据修订未变时不重写文件；每 60 秒仅刷新一次观察时间（心跳），避免页面因长时间无新结果被误判为离线。
- 刷新失败写入 `pending.json`，页面显示“页面可能已过期”，不宣称旧页面仍准确。
- `maintenance --apply` 清理超过 30 天的投影目录，只删除已知的 `projection.json`、`pending.json` 和临时文件，不递归删除未知文件。

## 3. 安全边界

- 仅绑定 `127.0.0.1`；端口默认由系统分配；不监听 `0.0.0.0`，无跨域响应头。
- 每次启动生成 `secrets.token_urlsafe(32)`；页面、投影读取和导出请求都校验令牌（HttpOnly、SameSite=Strict Cookie 或显式请求头）。
- 校验 `Host`（仅 `127.0.0.1:<port>` / `localhost:<port>`）以阻止 DNS 重绑定；导出的 POST 还要求同源 `Origin` 与 `X-Live-Request: 1`，防止简单 CSRF。
- 只接受 GET/HEAD 与固定的 `/api/export` POST；静态资源走白名单，不接受任意路径；请求体上限 64 KiB。
- CSP `default-src 'none'`，脚本样式仅 `'self'`；无外部 CDN、字体或图片；不记录访问日志和查询串，令牌不进入页面正文或来源链接。
- 来源文本只经 `textContent`/DOM 节点写入，不使用 `innerHTML`；来源链接在投影层和服务端两次限制为绝对 http/https；Excel 公式注入仍由既有 `safe_cell` 处理。
- 导出由查看命令调用核心 `runs.export`，在核心内重新校验交付政策；前端不判定资格，只传递关键词、国家和渠道。

## 4. 提速改动与测量

### 4.1 改动

- 页面构建复用提交时 `_refresh` 已算出的 `contactable`/`qualified` 选择（`_summary(detail=True)`），不再为每次轮询重复一次交付选择。
- 投影按 `companies_signature` 复用已保存页面；仅状态或时间变化时不重跑选择。
- 数据修订不变时跳过文件写入；运行秒表不计入修订。
- 处理循环内按 1 秒节流刷新投影，检查点后立即原子提交。
- 导出筛选参数进入核心幂等键和清单，筛选导出与页面使用同一交付政策。

### 4.2 受控测量（合成数据，禁止外部网络）

环境：本机 PostgreSQL 16、Python 3.12、单进程；`scripts/benchmark_live.py --batches 3 --per-batch 5`。

结构性优化（同机、同脚本、相邻两轮，各一次）：

| 指标 | 复用前 | 复用提交选择后 |
|---|---:|---:|
| 投影构建 p50 | 1.053 s | **0.0056 s** |
| 投影构建 p95 | 1.071 s | **0.0067 s** |
| 提交到页面文件就绪 p50 | 0.011 s | **0.015 s** |

当前实现连续三次运行（中位数，括号内为三次范围）：

| 指标 | 结果 |
|---|---:|
| 首批 5 家处理 | 8.12 s（3.04–8.28 s） |
| 15 家整批（入库、页面、导出） | 32.5 s（27.2–34.3 s） |
| 投影构建 p50 | 5.6 ms（4.9–9.4 ms） |
| 投影写入（构建 + 原子替换） | 13.8 ms（7.4–14.2 ms） |
| 提交到页面文件就绪 p50 | 14.7 ms（9.7–16.0 ms） |
| 页面最坏可见（就绪 + 2 s 轮询） | **2.01 s（2.01–2.02 s）** |
| 页面 JSON | 46.6 KB |
| 15 家正式导出 | 6.40 s（6.25–6.53 s） |

`scripts/benchmark_speed.py` 的 2.2.0 合成流水线基线（6 家 × 3 轮，无数据库）为：批次中位数 **1.41 s**，单家 p50 **0.176 s**。本次未修改 `pipeline`/`rules`/`web`，该基线不受影响。

### 4.3 结论与限制

- 受控条件下，页面投影构建约 **6 ms**，提交到页面可见约 **2.0 s**，满足规格 §4.1 的 5 秒目标。
- 首批/整批处理时间波动很大（首批 3.0–8.3 s，整批 27–34 s），主要来自本机数据库检查点、磁盘和主机负载；这些数字只能说明受控路径可运行，**不能**当作真实任务基线，也不能与 2.2.0 的真实任务耗时直接比较。
- **没有真实任务基线**：真实网页、Agent 搜索和来源限流不可复现，本记录不据此宣称首个/首批/整批的真实耗时已改善，也不承诺固定倍数。
- 15 家正式导出约 6.4 s，主要成本在核心交付选择与质量指标计算；200 家真实批次未测量。
- 每次任务提交仍会执行一次既有交付选择（`_refresh` 的原有成本）；本次消除了页面带来的第二遍成本，但没有重构该路径。

## 7. 已知缺陷与后续

1. 真实任务的首个/首批/整批耗时未测量；需要在用户明确给定的任务上按 §5.2 记录，并与 2.2.0 冻结版本对照。
2. AC-10 真实使用检视未完成；需要用户实际打开页面、搜索、复制和查看来源后记录问题。
3. 导出 15 家约 6.4 s；200 家未测，若成为瓶颈应分别测量交付选择、质量指标和 Excel 编码。
4. 页面单列表最多展示 1000 家，超出时给出提示；正式导出不受此限制。
5. 令牌随查看进程生命周期有效；进程重启即失效，这是有意的短时设计。
6. 心跳每 60 秒重写一次页面文件以刷新观察时间；数据修订不变时不重写。
7. 升级后首次为存量批次生成页面时，需要一次完整的交付选择；之后的状态刷新复用已提交选择和已保存页面。该一次性成本未在 200 家存量批次上测量。
