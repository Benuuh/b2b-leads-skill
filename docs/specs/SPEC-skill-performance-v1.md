# SPEC：B2B Leads Skill 通用执行与性能优化

| 项目 | 定义 |
|---|---|
| 文档版本 | 1.0 |
| 状态 | Proposed；本文件是实施规范，不代表功能已经实现 |
| 日期 | 2026-10-27 |
| 作用对象 | `b2b-leads` 的 Skill、控制器、本地采集核心及发布包 |
| 适用范围 | 跨行业、跨国家的 B2B 企业研究与公开商务渠道搜集 |
| 代码根目录 | `./` |
| 本轮交付边界 | 编写 SPEC；不修改运行代码、安装版本或业务数据，不恢复搜客 |

本文中“必须”表示验收要求，“建议”表示可通过试跑调整的初始选择。章节中的接口与配置标为 vNext 时，均是待实施设计，不能直接传入当前控制器。

## 1. 问题与目标

现有流程存在证据交接丢失、重复取证、补全超过交付需求、增量补证受阻、串行阻塞和交付过晚等问题。这些问题属于搜客执行机制，不应针对某一行业逐次修补。

**目标：同一 Skill 和核心加载不同任务配置，即可按相同的证据、状态、预算和交付机制研究不同行业企业。** 行业资格由配置表达；证据不足输出未知；默认只完成用户要求的最小充分交付。

优化必须同时改善可测性能并保留资格准确性、来源追溯、身份去重、抑制规则和运行恢复能力。只缩短提示词、提高并发或放宽资格不构成完成。

非目标：任意类型 Skill 的统一调度平台；无限表达式规则引擎；新增付费数据源、API key、外联、CRM 写入、常驻后台服务；重置旧批次计时或升级不兼容的旧系统数据库。

## 2. 通用机制与任务配置的边界

| 固定在 Skill／核心的机制 | 由任务配置决定 |
|---|---|
| 证据合同、主体绑定、出处与完整性检查 | 行业、产品、服务、客户类型及地域范围 |
| 满足／不满足／未知／冲突的判定机制 | 必要资格、排除条件、总部或分支政策 |
| 发现池、逐条预检、证据优先、缺项补查 | 路线、认证、制造能力等任务特有条件 |
| 统一身份、增量证据、幂等与复评 | 允许的渠道、是否必须指定岗位或具名联系人 |
| 预算、租约、限流、暂停、失败分类 | 目标数量、受支持范围内的执行与交付参数 |
| 一致的交付选择和版本化快照 | 语言、格式、销售排序与切入建议 |

不得在通用层硬编码“美国总部”“中国起运”“+1 电话”“只要制造商”或“必须邮箱和电话都有”。路线只能是某个任务启用的事实类型；其他任务不加载路线条件。

销售优先级不属于必要资格，排序分数不能覆盖不满足、未知或冲突的资格判断。

## 3. 分层职责与文件改造范围

调用链保持：`Skill → verified controller → CLI → runs → pipeline → rules / web / delivery / persistence`。

| 层 | 实施职责 | 不应承担的职责 |
|---|---|---|
| `skills/b2b-leads/SKILL.md` | 解析用户目标；选择或生成任务配置；研究计划、证据交接、检查点、早停和交付路由 | 复制核心资格算法；宣称未执行的能力已经可用 |
| `skills/b2b-leads/references/` | 任务配置、证据合同、控制器命令和失败恢复的详细参考 | 将全部详细规范塞进入口上下文 |
| `backend/app/schemas.py`、`cli.py` | 版本化输入、能力发现、预检、错误路径和有界命令参数 | 静默接受或忽略不支持的条件 |
| `runs.py`、`pipeline.py` | 冻结配置；证据优先；增量补证；租约、预算、处理与恢复 | 在网页层写数据库或另建资格分母 |
| `rules/`、`delivery/selection.py` | 共享主体、资格与渠道判断；输出理由和缺项；统一交付选择 | 用 Agent 自报通过代替证据核验 |
| `web/`、`persistence/` | 有限联网、快照、限流、预留、短事务和审计 | 绕过 robots、来源冷却或预算 |
| `scripts/skill_release.py`、安装流程 | 将 Skill 与核心冻结为可校验版本；验证安装入口 | 直接覆盖安装目录后绕过完整性检查 |

更新 Skill 源码时同时维护相关参考。安装版只能在重新冻结、打包及安装后获得能力；只修改开发目录不算发布完成。

## 5. 任务配置合同：SegmentSpec vNext

### 5.1 兼容与冻结

- 现有无版本输入按 v1 解释；现有字段、限制和语义保持不变。
- vNext 新增 `spec_version: 2`、`qualification_policy`、`evidence_policy`、`execution_policy`。schema 必须明确接受并校验这些字段。
- 创建 run 时保存规范化配置、配置 hash、规则版本和执行发布版本。旧 run 的原配置 hash、原请求 hash、目标数量及累计预算不得重写。
- 新能力默认只由新 v2 run 显式启用。旧 run 不自动转换为新的资格政策；不支持的版本必须报错。
- 不在本期增加任意脚本、SQL 或 Python 表达式执行能力。

旧 run 的 `process/export` 必须走明确的 v1 兼容决策路径，沿用冻结的资格、渠道、去重与计数语义；缺少版本字段的历史 run 确定映射为 v1，而非当前最新版。兼容路径不能用新增 v2 条件重判旧结果。无法保持兼容时明确拒绝处理或导出并说明原因，保留可读取状态，不隐式重启或降级。显式 `reassess` 仍按其既有审计合同记录执行版本及前后变化，与自动升级区别记录。

### 5.2 必要资格表达

每条条件包含 `id`、`field`、`operator`、`value`；条件集合使用 `required_all` 与 `exclude_any`。首期不做无限嵌套 DSL。字段与运算符必须来自能力注册表，有类型、适用主体、证据规则和未知处理。

首期通用字段至少包括：经营国家、总部国家、注册国家、主体关系、业务模式、自身提供的产品／服务、服务的客户行业。国家类型使用 ISO 两位码；主体关系区分独立企业、子公司、分支及未知。事实必须绑定对应实体，不能把集团、客户或合作伙伴的能力转移给候选。

关键词用于发现；不能仅凭关键词命中证明产品、服务、认证、总部或采购需求。Agent 可抽取有原文依据的语义事实，核心须核验主体关联、出处及该谓词要求的证据；无法可靠核验则返回 `unknown`。新增专业谓词需要注册对应校验器，不能宣称可自动验证所有行业资质。

`countries` 与 `qualification_policy.country_scope` 配合解释地域目标，可选经营地、总部或注册地；v1 的国家语义不追溯重释。相互矛盾或未支持的条件返回路径明确的错误。

决策真值规则必须固定：必要条件出现 `fail` 则不符合；排除条件出现 `pass` 则排除；必要条件仍有 `unknown/conflict` 时进入待核。每条排除条件可声明有限枚举 `unknown_policy: review | allow_unconfirmed`，默认 review。仅在用户意图明确为“排除已知某类”时可显式选择 allow_unconfirmed，未知表示尚无命中证据，不改写为事实 `fail`，并在报告保留未知。`conflict` 在两种政策下都必须复核。仅当必要条件全部 `pass`、没有排除命中或待核条件，再满足渠道政策，才可计入交付。空排除集合无需补证。必要条件不支持 allow_unconfirmed，不得静默选择更宽的排除语义。

重复配置必须有单一语义：未提供新政策时由 v1 字段生成等价缺省政策；同一 v2 输入同时显式提供旧字段与新政策的同义参数且值冲突时拒绝。例如顶层 `freshness_days` 与 `evidence_policy.freshness_days` 不得各自生效。所有默认值和边界在能力输出中可查询。

### 5.3 示例：德国工业包装制造商

以下为拟议 v2 输入示意，尚不是当前 CLI 可接受的输入：

```json
{
  "spec_version": 2,
  "name": "德国可重复使用工业包装制造商",
  "industry": "industrial packaging",
  "countries": ["DE"],
  "quantity": 200,
  "paid_sources": false,
  "budget": 0,
  "qualification_policy": {
    "country_scope": "headquarters",
    "required_all": [
      {"id": "hq", "field": "entity.headquarters_country", "operator": "in", "value": ["DE"]},
      {"id": "maker", "field": "business.models", "operator": "includes", "value": "manufacturer"},
      {"id": "product", "field": "offering.products", "operator": "provides", "value": "reusable industrial packaging"}
    ],
    "exclude_any": [],
    "contact_policy": {
      "mode": "any",
      "allowed_types": ["business_email", "business_phone", "contact_form"],
      "named_person_required": false
    }
  },
  "evidence_policy": {"freshness_days": 180},
  "execution_policy": {
    "company_workers": 2,
    "native_inflight": 2,
    "snapshot_every_new_qualified": 10,
    "snapshot_interval_seconds": 900
  }
}
```

上述字段与算子必须在能力注册表中有实现；其他领域只在已有能力范围内配置使用。不能把自然语言 `provides` 当作已经实现的万能语义判断。

### 5.4 渠道与补全政策

- 默认延续现有交付底线：一个有充分来源且质量合格的公开商务渠道。
- 用户可配置允许渠道类型、任一／全部类型、指定岗位或具名联系人要求。`mode=all` 的含义是所有列出的渠道类型均须有合格值。
- 用户明确要求邮箱与电话或特定岗位时必须满足；不能为了提速自动降级。
- 不同国家的号码、总部、分支与来源政策不得继承上一任务的特例。
- 指定要求未满足时列出缺项；额外渠道、社媒、员工规模等只在任务要求或可选后补阶段搜集。

## 6. 证据合同与发现池

### 6.1 EvidenceBundle v2

一份证据包至少包含：

| 对象 | 最小内容 |
|---|---|
| `entity` | 稳定内部 ID／外部暂定键、观测公司名、法律主体与分支线索、官网关联证据 |
| `facts[]` | `fact_id`、主体、字段、值、关联谓词、证据 ID、冲突关联 |
| `channels[]` | 类型、原始值与规范值、所属企业／办公室／人员、证据 ID |
| `observations[]` | `evidence_id`、主体、字段/值、完整 URL、来源类型、原文摘录、带时区采集时间、方法、页面引用 |
| `page_refs[]` | 快照 ID、内容 hash、获取方式、采集时间、完整性与保留状态 |
| `lineage` | 查询／工具观察／chunk 标识；规范版本、输入 hash，不含凭据 |

不得把单纯断言、搜索摘要、置信分数或自由侧记当作资格证据。搜索摘要仅可进入发现池。每个交付渠道必须有包含实际渠道值的独立观察；表单须观察到所需输入，Contact 链接不等于有效表单。官网归属与业务资格分别取证。

入口对未知正式字段必须报告错误；扩展信息使用明确命名且不会参与资格判断的扩展区。不能继续静默丢弃证据。自由笔记可保存，但不替代正式事实。

原生页面不能提供完整 HTML 时，可保留其实际观察载荷、URL、时间与 hash，明确来源种类和可信边界；不得伪装成官方网页完整快照。观察 hash 只能证明留存内容未变，不能自行证明内容真实或网站归属。

### 6.2 状态流转

| 状态 | 含义与下一步 |
|---|---|
| `discovered` | 发现身份线索，允许摘要；不计已准入或合格 |
| `evidence_pending` | 已确定需要补哪些主体、资格或渠道证据 |
| `append_ready` | 通过输入预检，可按原子 chunk 提交；不代表资格通过 |
| `admitted` | 核心已接收，按正常资格与交付流程处理 |
| `needs_evidence` / `needs_review` | 事实缺失、来源受限或冲突，进入相应补证队列 |
| `qualified_contactable` | 所有必要资格满足、无命中排除、渠道满足政策、经抑制与去重后可交付 |
| `excluded` | 有证据证明必要资格不满足或命中排除 |

这是研究状态与交付状态模型；实施时不得直接改写现有 job 状态含义，可采用独立研究索引和决策字段。

研究清单大于检查点上限时，存入既有忽略的运行工件目录，以路径、hash、schema 版本及小型索引写入 checkpoint；不得突破现有 20,000 字符检查点限制。

逐条预检返回每条记录的索引、错误路径、理由码、是否可准入和规范化 hash；研究协调器隔离无效草稿后提交有效子集。`append` 继续保持原子与幂等，不静默部分提交，也不擅自重写已有 chunk 输入。

## 7. 证据优先、停止与增量补证

### 7.1 正常处理顺序

1. 校验配置、身份、证据完整性、抑制与已知重复。
2. 复用有效保存证据，对每条必要条件输出 `pass`、`fail`、`unknown` 或 `conflict` 及理由。
3. 必要资格全部满足且渠道质量符合政策时直接完成；没有缺项不得默认再抓官网。
4. 对未知生成字段级补证计划；真冲突进入复核，明确失败则排除。
5. 只获取补证计划需要的允许来源；每次新增证据后重新判断是否已达停止条件。

缓存必须受来源访问约束、实体、证据 hash、时效、规则版本及抑制状态约束。不能把另一实体、另一账号上下文或不允许复用的数据拿来通关。采集时间与最近评估时间分别保存，复评不刷新原采集时间。

“零网络完成”要求所有当前交付要求都已有有效证据与验证结果。若渠道质量要求 DNS/MX 等检查且没有有效缓存，该检查仍是缺项，不能为了零请求绕过。

### 7.2 身份与补充证据

统一身份解析被研究索引、核心与导出共同使用：法律后缀规范化；仅按已证实别名归并；总部、分支和办公地点分开；同域不同法人不误并。候选初始序号保持稳定，不能让并发完成顺序改变归属或去重结果。

新增 `supplement` 的拟议语义：针对既有公司，以 `expected_revision`、证据增量 hash 和幂等键追加新证据；保留旧证据、原时间和审计；只重算受影响阶段；没有新增证据不重复抓取。版本不一致时返回冲突并要求重新读取；不能靠修改公司名制造新候选。

补证不增加唯一候选数，但其实际联网继续消耗既有请求、页面和时间预算。输入关闭后拒绝新增证据；暂停时可保存证据但不得隐式恢复派发。进行中的旧修订结果不能覆盖新修订。

已存在的 `reassess` 保留只读保存输入/快照、零 HTTP/DNS 的语义和最多 20 家限制；它不接受新证据、不修复失败任务，不作为 `supplement` 的替代品。

## 8. 有限并发、预算与失败处理

### 8.1 调度

- 初始建议两名独立研究 worker，共享候选认领与快照索引；原生工具单入口限制在途数，初始 2，支持按错误与容量状态降至 1。角色是逻辑职责，不要求每个环境都具有多 Agent。
- 每个子任务只携带客群条件、实体认领、已有证据引用、缺项与剩余预算，避免复制完整历史或重做已完成研究。定期保存紧凑查询计划与状态索引；跨任务传递完整 URL 和稳定观察 ID，不传递仅在原任务有效的页面句柄。此改造不要求切换用户指定模型。
- 后台先支持 2 个跨域企业 worker，验证通过后可配置至最多 4 个。单企业页面按依赖顺序处理；无并发能力时必须明确串行降级，不伪造并发统计。
- 一个有界 `process` 命令协调所有后台 worker，不创建常驻服务，也不直接同时运行多个互斥的旧 `process`。
- 短事务领取、独立租约与心跳、联网和解析在事务外、短事务保存；校验租约 token、实体修订和幂等键，旧执行者不得覆盖新结果。
- 同一 host 延续跨 run 的全局限流、robots 和 429 冷却，不因并发或新进程失效。

### 8.2 预算与截止时间

保留现有限制：单 chunk 最多 20 候选、单次 process 最多 20 jobs、单企业累计页面上限含失败与重试、候选上限为目标三倍、默认累计非暂停墙钟 8 小时、零付费。总页数等具体限制读取已保存 run，不在 Skill 另写第二份分母。配置不能自动扩张核心上限。

并发前必须原子预留预算；发送前检查暂停、租约、剩余时间与额度；在途结果及已发生费用按真实请求记账。目标已满足或截止后停止新领取和新发送，对在途请求采用明确的有界完成规则。重试、robots、重定向等必须使用适用的物理请求计量，不能只数成功内容页。

将命令截止时间传递到 crawler、限流等待和 HTTP；请求超时不得超过适用剩余预算与现有上限的较小值。无法取消的原生工具只停止后续派发并幂等归档迟到结果；不得把逻辑超时宣称为底层已取消，不得无限堆叠替代请求。

暂停、恢复沿用原 run，不重置累计计时。扩展时间只能走现有显式授权和审计流程；本功能不能自动延长。

### 8.3 分类与熔断

至少区分：输入无效、事实未知、主体冲突、暂时网络故障、访问禁止/robots、工具或模型容量、预算耗尽、快照缺失/过期/损坏。只有有证据的事实不满足可作为资格失败。

暂时故障在预算内有限重试并遵守 retry-after；受限来源改用允许的替代证据或保留待核。连续工具故障触发熔断：停止重复派发、保存检查点、交付现有结果并解释阻塞。不绕过登录、验证码或来源访问限制。

熔断窗口、阈值与冷却时间使用有界配置并记录配置来源，试跑后调整；不能事先宣称某一阈值对所有来源最优。

## 9. 拟议控制器接口与兼容要求

以下是新增/扩展接口设计，实施前当前 CLI 不支持：

| 接口 | 要求 |
|---|---|
| `capabilities` | 无业务写入，返回支持的 spec/证据版本、字段/算子、渠道政策、并发与限额能力 |
| `validate-input --spec-json ... --input-json ...` | 离线逐条校验，无 HTTP/DNS/业务写入或隐式维护；返回可提交子集和逐条错误，不承诺资格已经满足 |
| `supplement --run ... --company-id ... --input-json ... --operation-key ...` | 仅 v2 能力；输入含 expected_revision；原子追加、审计和缺项复评，遵守输入关闭与暂停语义 |
| `process ... --workers N` | 保持原有参数和上限；受支持版本按保存政策有界并发；不支持时明确报错 |
| `status` / `export` | 保留旧字段，添加版本化研究指标、缺项及配置摘要；完成数与导出共用选择规则 |

现有 `SegmentSpec`、`ResearchInput` 使用严格顶层校验；候选规范化还会过滤未声明字段。因此新字段必须先进入正式 schema、控制器能力和持久化设计，不能只写在 Skill checkpoint 里便宣称核心已执行资格判断。

现有 chunk 与操作键保持原始输入 hash 重放语义。旧版本不知道的新字段/接口必须明确拒绝；禁止自动剥离条件后按更宽口径运行。

默认 Excel 的四表、中文交付及公共渠道质量声明保持兼容；详细谓词决策与执行指标可放质量报告或版本化附加结构，不直接破坏已有列含义。

## 10. 快照交付与指标合同

### 10.1 快照

建议初值：每新增 10 家可交付企业，或距上次快照 900 秒且投影有变化时导出。没有新增有效结果则报告当前缺口与阻塞，避免重复制造文件。

该机制在命令/研究协调器的安全检查点执行，不引入常驻定时服务。协调器停止或底层工具长时间不返回时，不能保证定时触发；必须记录超期和原因。

快照、最终导出、完成判断始终共用资格、渠道、去重与抑制政策。报告分别显示快照时点与最新进度；不足目标仍交付真实结果与缺口，不改分母。

### 10.2 计量

新增 `metrics_version`，保留现有指标语义。例如当前 `discovered` 表示已准入数，不得改成搜索发现池大小；新增 `discovery_seen`、`append_ready`、新发现合格数、补证转合格数、离线复评转合格数等独立字段。

必须记录：

- 各阶段进入/退出、队列等待、工具等待、解析、数据库/汇总和导出耗时；并发阶段不能直接相加解释总墙钟。
- 用户等待墙钟、保存 run 的非暂停墙钟，以及明确记录的空闲/容量/调试区间。时间区间未知时保持未知，不事后推断。
- 原生工具 invocation、查询数、打开 URL 数、后台物理 HTTP、DNS/MX、内容页尝试、缓存复用及成功/失败；指标含单位、覆盖区间和观测来源。未知为 null，不填 0。
- 稳定实体 ID 下的新增唯一合格数、资格/渠道缺项、排除和失败原因、每个来源/查询的有效产出。

主要吞吐率：`新增唯一合格企业数 / 同一区间 run 非暂停墙钟小时数`。另列离线救回与新发现产出，不把多个 worker 工时当成协调器墙钟，也不剔除工具等待来美化速率。

## 11. 验收标准

| 编号 | 场景与通过条件 |
|---|---|
| AC-01 跨行业配置 | 使用第 12 节两份非货代配置，走同一正常入口完成预检、资格、补证与导出，无须修改行业业务代码；未注册条件明确拒绝 |
| AC-02 证据与未知 | 已交付企业的所有必要条件和计数渠道均可追溯；只有地址、客户新闻、摘要或断言的反例不通过；事实未知与来源故障不被判为事实失败 |
| AC-03 逐条预检 | 四条有效记录与一条缺摘录草稿同时输入；返回四条可提交及一条错误；有效子集原子提交，重放不重复 |
| AC-04 证据优先 | 固定 20 家离线标注样本，覆盖正例、反例与未知；充分且有效证据零 HTTP/DNS 完成；缺渠道验证的样本只生成对应缺项，不放宽规则 |
| AC-05 最小充分停止 | any 政策下一个有效表单可完成；all 或具名岗位政策下不足则继续缺项补证；无任务要求时不额外抓社媒或更多联系人 |
| AC-06 身份与补证 | 同域两个法人保留；有证据的别名归并；补充证据可使未知重新判定；输入重放不新增唯一公司，过时修订结果不能覆盖新修订 |
| AC-07 并发与预算 | 两 worker 在剩余一次请求额度、暂停、租约过期、目标已满和截止边界下不超发；真实在途消耗可追溯；跨 run host 冷却有效 |
| AC-08 恢复与发布 | 中断后相同 run/操作键可恢复；在相同输入、抑制与时效基准下，旧 run 升级前后资格、排除与导出投影一致，累计计时保持；新版本经安装入口完整性校验后能力可见，开发目录变化不隐式生效 |
| AC-09 快照与计数 | 增量阈值或安全检查点时间阈值满足时产出实际快照；快照行数与同版本交付投影一致；没有变化不重复导出；缺口按原目标报告 |
| AC-10 性能报告 | 固定样本与受控在线试跑分开报告；包含基线、配置/规则/发布版本、质量结果和耗时单位；未知指标为 null，不能凭不同样本宣称固定倍数提速 |
| AC-11 排除未知政策 | 默认排除条件未知则待核；显式 allow_unconfirmed 时，必要条件与渠道均满足可交付并披露排除未知；任一模式的冲突均待核 |

验收优先复用现有测试与既存脱敏样本，只新增覆盖合同、资格边界、增量补证及并发安全的必要行为测试。

## 12. 非货代配置验收样例

### A. 德国工业包装制造商

- 必要：德国总部；自身制造可重复使用工业包装；至少一个有来源的商务渠道。
- 排除：只有经销能力且不制造、已有客户。只有德国销售办公室不能满足总部条件。
- 样本：同域两个法人；集团总部与工厂地址不同；产品文章只介绍客户的包装；有有效表单但无邮箱。
- 预期：分别验证总部、制造能力、主体绑定、身份去重和 any 渠道政策；不出现路线或美国号码条件。

### B. 阿联酋零售业 IT 集成服务商

- 必要：阿联酋实际经营；由该实体提供 POS／门店系统集成；有零售客户服务证据；至少一个公开商务渠道。
- 政策：允许国际集团当地分支；不要求阿联酋总部；有效商务表单可以是唯一渠道。
- 样本：只有软件产品介绍；实施由合作伙伴负责；集团与当地分支共域；无邮箱但有有效表单。
- 预期：总部未知不妨碍允许分支的任务；伙伴能力不转移给候选；合格表单达到停止条件。与 A 使用同一核心，仅配置不同。

以上是验收场景，不是假冒已研究客户；离线使用受控样本。实时搜客需要具体执行任务，不因编写或实现本 SPEC 自动启动。

## 13. 实施、发布与速度结论

1. **M1 合同与编排**：能力发现、v2 schema、研究状态、预检、阶段计时、失败分类与快照触发。兼容旧 schema，不能先丢掉旧接口。
2. **M2 证据与决策**：共享资格/渠道政策、缺项计划、正常路径证据优先、统一身份与 supplement。完成 AC-01 至 AC-06 的离线验收。
3. **M3 并发与恢复**：独立任务租约、预算预留、deadline 和迟到结果处理。完成 AC-07 至 AC-09 及项目要求的回归检查。
4. **M4 发布**：更新 Skill 与参考，冻结核心/Skill release，安装后通过真实入口做离线能力与回放验证；保留可验证的回滚方案。存在 schema 迁移时，先备份、验证旧 run 可读及发布版本可用，禁止用旧核心写入不支持的新 schema。
5. **M5 试跑与评估**：在明确的实时研究任务下用 30–50 个新候选验证吞吐与失败率；保持真实目标和已有 quantity 下限，试跑不冒充目标全部完成。根据结果决定 2→4 worker 及 P2 优化，不自动续跑旧批次。

首批延迟、每家请求数、P50/P95、缓存复用和合格产出率是待实测指标；20–30 分钟首批 10 家可作受控试跑目标，不是通用 SLA。200 家或其他目标的 ETA 只在有代表性在线样本后，按剩余数量与实测新增合格速率估算并注明不确定性。

性能验收分两类：固定离线样本比较重复计算和不必要请求；在线样本比较完整等待与新增产出。质量标注及必要条件必须同时通过。没有有效对照或工具不可用时，只报告结果与限制，不填造提速百分比。
