## 1. 目标与保证边界

每个新批次开工前，先展示生效的客群口径、依据、行业边界、来源与可得性判断、风险和待定项；用户看到后明确确认，才创建 run。需求完整时也执行这一流程。确认后冻结的配置与展示的口径必须一致；任何确认范围内的值变化都要重新展示并确认。不放松现有资格、证据、渠道和预算规则，不新增数据库迁移。

**信任边界**：本方案面向单用户、本机、可信 Skill/Agent。Skill 负责展示口径并判断用户在展示之后是否明确确认；核心仅校验传入哈希与当前配置是否一致。哈希可被任何调用方计算，不能证明用户确实确认、确认人的身份、确认消息内容或确认发生的准确时间；直接调用核心可以绕过交互。`plan` 中的记录只表示调用方提交了匹配的确认哈希，并不构成独立的身份审计。若未来要求可独立核验的确认，须另行设计可信身份、会话确认事件与防伪机制。

非目标：多轮问卷、多人会签、保证找满目标、改变已冻结批次的资格和计数语义、冻结运行中已有的全局抑制名单。无依据时不估计能否找满。

### 1.1 本次补充：把取证能力作为交付风险

目标企业数量充足不代表能按当前规则和网络环境完成取证。已知美国货代任务中存在国家表达识别、JS 渲染、域名访问受阻和搜索工具不可用等潜在瓶颈；这是待复现的任务观察，不代表所有美国货代网站或所有环境均如此。当前 `country_supported` 对国家证据匹配 ISO 两位码及 `pycountry` 名称，尚不具备完整的别名和结构化地址语义；需要针对具体输入复现，不能笼统地把所有未命中都称作「判定不符合」。

本规格新增执行前可取证性提示与限额内诊断要求，同时定义须另行实现和验收的取证能力。仅上线确认流程不能宣称解决本节所述吞吐问题；若能力尚未完成，确认摘要须如实说明限制，不得承诺完成速度或数量。涉及规则语义的修复应以独立规则版本和兼容方案交付，不得静默改变已冻结批次的判定。

## 2. 场景与交互状态

1. 用户提出新任务后，Skill 抽取配置，查询 `capabilities`，调用离线 `brief`，展示确认摘要和客群分析，再等待答复。
2. 用户看到该版摘要后明确说「确认」「就按这份建议执行」或「直接跑」，视为确认当前版本；沉默、含糊答复或仅提问均不算确认。展示前说的「别问了直接跑」属于事先授权，不能确认尚未展示的具体口径；仍须展示并等待后续明确答复。
3. 用户修改任一项时，重新预检并展示新的完整生效摘要、变化及必要分析，再等待确认。允许多次修改，不限制轮数；每轮把问题合并提出，不逐项追问。
4. 多项推断或缺失条件超过 3 条时，先合并为一轮澄清；必要条件仍不明确时不开跑。每次展示后的确认只适用于该次摘要对应的哈希；无论用户是否说了「确认」，如果同一答复同时修改配置，先按修改处理并重新展示。
5. 用户中断或只提问时不建 run、不启动研究计时；会话上下文尚可恢复时可继续，无法可靠恢复完整确认范围时重新生成并展示，不能推断已确认。用户确认后重试同一 `run_id` 与同一配置应幂等。
6. 既有 run 的续跑、补证、重评及导出沿用其已冻结口径，无需补做新建确认。

## 3. 确认摘要与客群分析

### 3.1 确认摘要：生效值的唯一来源

`brief` 根据规范化 spec 和创建时实际生效的固定计划默认值，确定性生成结构化 `confirmation_summary`；Skill 将其完整呈现为中文，不得增加、删改或反转条件。摘要应使用户无需阅读 JSON 就能检查所有影响以下事项的**生效值**：

- 行业与品类、国家和国家口径、企业类型、产品/服务、下游行业、规模、子公司/分支要求、所有必要条件及排除条件，包括逻辑关系和未知值处理；未设条件明确标记「不限」或「未指定」，不得默认为排除。
- 目标数量、候选上限、渠道类型及 `any/all`、具名联系人及岗位要求、证据有效期和其他影响合格判定的证据策略。
- 初始累计研究时间、单企业和批次页面上限、付费及金额预算。当前基线初始时间为 8 小时，候选上限为目标数量的 3 倍；由生成摘要和创建计划共用的代码提供实际生效值，不从模型记忆填写。
- 其他执行参数及默认值也必须可查看；可置于「执行参数」小节，但不能省略或用模糊表述代替。摘要应包含版本、完整 `spec_hash` 和 `confirm_hash`；哈希供核对，用户不必手工输入。

对 v1/v2 均展示实际生效语义；不把 v1 强制改写为 v2，也不改变原有哈希语义。未注册字段或运算符按现有校验规则拒绝，不能在文案中新增未落入配置的硬条件。技术字段的展示映射必须覆盖全部支持字段；新增影响确认的字段而没有映射时，预检应失败，不得静默遗漏。摘要、默认值和创建计划必须从同一份有效配置生成，测试逐字段核对；不得由模型自由改写生效值。

动态全局抑制名单独立于 spec，会在运行中变化，不由本次哈希冻结。展示时说明「另适用当前全局抑制名单，运行中可能变化」；不得宣称名单已冻结。用户提供的现有客户文件只报数量和文件哈希，不展示企业、联系人、邮箱或电话；只有现有系统实际支持并接入该排除机制时才可声称其生效，否则须明确未生效并在确认前解决，不得仅凭展示或文件哈希声称已排除。

### 3.2 分析与依据

在生效摘要之外，Skill 组织简短分析，覆盖：

| 区块 | 要求 |
|---|---|
| 字段来源 | 对用户可理解的各项标注「用户原话」「默认值」或「推断」。推断项列入待定并提请确认；有冲突时先澄清。 |
| 行业边界 | 说明相邻类型及已知正例、反例；无可靠依据时明确「未知」，不强造例子。 |
| 来源与可得性 | 可提供关联协会、展会或目录及其依据；估计数量时标明依据、时间和不确定性。证据不足则写「尚未核实」，不猜能否找满。 |
| 渠道现实 | 有依据时说明常见渠道及限制；未知时明说。不能借此更改用户要求的渠道政策。 |
| 风险、待定与建议 | 每轮最多列 3 个合并后的关键问题；一句推荐，可附一个更宽或更窄的备选，备选不得混入当前生效配置。 |

`brief` 离线，不判断市场事实。Skill 如有必要可另行查证，注明来源和查验时间；查证与 `brief` 分开，不创建 run、不消耗该 run 的预算，也不能声称完全没有外部访问成本。没有查证时使用「未知」或「待核实」，不把估计写成承诺。低于支持的数量下限时说明限额并请用户修改；预计有缺口时说明依据与建议，不擅自改目标或静默降级。

来源标签由 Skill 根据对话及预检的 `defaults_applied` 建立字段来源映射：用户明确提供的值标「用户原话」，未提供且由核心填入的标「默认值」，由 Skill 补出的标「推断」。不得仅凭最终值猜来源；无法确定则标「来源待核」并请用户确认。映射与草稿仅保留在当前会话上下文，不作为可信审计证据、不入业务库；无法恢复时重新构建。

### 3.3 展示示例

实际摘要必须包含 §3.1 全部生效值，下面只展示交互形式，不作为完整字段模板：

```text
客群与资格：[从 confirmation_summary 完整展示，并标明来源]
排除与未知值处理：[从 confirmation_summary 展示]
数量、渠道、证据要求：[从 confirmation_summary 展示]
初始时间、页面与付费预算：[从 confirmation_summary 展示]
执行参数：[从 confirmation_summary 展示]
全局抑制名单：运行时适用，可能变化。
配置哈希：[spec_hash]；确认范围哈希：[confirm_hash]

研判：[有依据的边界、来源和风险；未知项标明待核实]
待你确认：[合并后的待定项]
确认按以上口径开跑？可以回复「确认」，也可以说明要修改的地方。
```

### 3.4 可取证性检查与实际瓶颈

确认前除口径外，简短说明目标国家的证据规则、允许的来源和当前已知工具限制。区分「目标市场可得性未知」与「当前环境无法高效发现或核验证据」；无法判断时写未知，不把搜索不可用解释为没有公司。`brief` 始终保持离线。Skill 可在展示前使用当前可用工具做小规模只读诊断：记录所用来源、时间、样本数与失败类型；不创建 run、不启动 run 计时，外部访问仍有时间及请求成本。未做诊断或样本不足时明确标注，不能外推市场数量、完成时间或失败率。

诊断依次检查：可用搜索或目录入口；少量相关公开页面的 HTTP 获取及正文可读性；在允许且具备能力时检查渲染后的可见正文；国家、企业主体和所要求角色能否从原文核实。小样本结果只是定位风险，诊断失败不自动放宽资格规则；用户仍可确认按已知限制开跑，或调整口径后重新确认。现有客户名单不用于公开诊断查询。

取证能力按以下优先级纳入后续实现；不要求把新能力伪装成已经上线，也不能通过展示替代修复：

1. **国家表达和地址识别（优先）**：在版本化规则中识别明确的 `USA`、`U.S.`、`U.S.A.`、`United States` 及合适上下文的 `US` 等写法；结构化地址中的州名、州缩写和邮编仅在地址上下文足以消歧且来源明确关联目标企业时支持美国地点推断。不得仅凭裸 `CA`、`US`、州名、电话号码、域名后缀或运输目的地判定企业所在地；例如 `CA` 可指加拿大或加州，正文里的 `us` 可为代词。保留原始摘录、URL、采集时间、来源类型及标准化依据，不能把标准化后的国家代码伪装成原文。
2. **地点语义**：经营地、总部和注册地分别验证。可靠证据指向本企业美国办公室可支持美国经营地；普通办公室地址不足以证明总部或注册地。货运线路、服务覆盖、客户、合作伙伴、集团其他实体及否定或历史陈述不能自动证明目标主体当前位置；证据不足为 `unknown`，有可靠相反证据时才按现有规则判定冲突或 `fail`。协会/官方登记/企业官网等来源是否可用于某字段，以现行证据政策及主体绑定为准，不强制所有事实只能来自官网，也不因来源标签单独视为充分证明。
3. **受限的渲染回退**：先复用已有证据并尝试普通抓取；仅当需要的正文缺失且具备能力时，对允许访问的公开页面执行有上限的 JS 渲染。沿用 robots、每域限流、429、页面和总时长预算；记录实际尝试、等待和失败原因。没有渲染能力或被拒绝时保留待核，不绕过登录、验证码、访问控制或网络限制，不把抓取失败当作负面资格证据。
4. **发现与网络退路**：搜索不可用时，优先检查可用的公开协会名录、展会名单和其他合法目录，批量发现候选；搜索摘要只作线索，事实仍须来自可核验来源。对 DNS、超时、403/429、网络拦截、JS 空正文和搜索不可用分别计数，限次重试；替代来源能提供符合政策的主体与事实证据时可使用，不能访问或缺证据则保留待核并报告。所有入口都不可用时保存检查点并暂停，不无限逐页人工尝试或编造事实。
5. **度量与旧批次**：分别记录发现、页面获取、渲染、国家证据、其他资格和渠道的耗时/失败/待核数量，以及单位时间合格数；未知值保持未知。确认是规则误判、页面不可达还是候选不足，再选择优化。规则修复须新版本、可复现样本、回归测试与旧批次兼容方案；旧 run 默认继续其冻结规则。对已存证据可否采用新规则重评，须通过单独的显式迁移或新批次方案决定并核对影响，不得直接修改原 spec、悄悄改变历史计数或假定现有 `reassess` 已具备跨版本能力。

## 4. 数据契约与生命周期

### 4.1 预检与哈希

新增 `brief --spec-json FILE`，只读取输入文件与本地静态能力/规则，完全离线：不连接数据库、不执行准备或维护、不发起 HTTP/DNS、不创建 run、不启动计时。校验成功返回规范化 spec、`spec_hash`、`confirmation_summary`、`confirm_hash`、`defaults_applied`、`validation` 和可由输入及规则推导的 `pending_hints`；不生成市场结论。校验失败返回与现有错误契约一致的字段路径、错误码和限额，不产生可用于创建的确认哈希。

- `spec_hash` 继续使用现有规范化 spec 哈希，保证既有 v1/v2 语义及已冻结记录兼容；明确规范化、序列化、编码、摘要算法和版本，提供固定测试向量。保持现有 `_hash` 算法及历史测试语义，避免为此改写旧批次哈希。
- `confirm_hash` 是独立的版本化确认范围哈希，覆盖 `brief_version`、`spec_hash`、创建时生效的规则版本以及影响用户确认的固定计划值（初始时限、候选倍数、页面上限等）；规则版本也须在摘要中展示。不包含 run ID、来源标签、文案、当前时间或可变的全局抑制名单。确认摘要由同一有效输入及固定计划值生成；字段、顺序和默认值规则须版本化，变更确认范围时更换版本。确认与创建之间若规则版本变化，旧哈希失效并要求重新展示确认。
- `brief` 和 `create` 共用纯函数完成解析、规范化、有效计划默认值、摘要和哈希计算。同一版本和输入在不同进程或重启后结果一致；任何确认范围内的有效值变化使旧 `confirm_hash` 失效。无语义变化的 JSON 格式或键顺序变化不要求重新确认。
- `capabilities` 增加 `segment_brief_version: "segment-brief-1"`，返回可确认范围与实现版本。新增字段、规则或默认值导致生效摘要变化时，必须同步更新版本及测试。

### 4.2 创建、失败与幂等

`create` 必须接受 `--confirm-hash`。CLI 在 `prepare`、周期维护、连接数据库或其他有副作用操作之前读取输入、规范化并校验哈希；缺失或不匹配返回 `SEGMENT_NOT_CONFIRMED`（409）及当前 `confirm_hash`（仅在输入有效时），不返回无法从哈希反推出的差异字段。规范化或输入无效按原错误契约失败，同样不得启动数据库操作。参数解析阶段缺少参数也须输出统一机器可读错误，并保证无副作用。

核心 `runs.create` 自身也必须强制相同校验，并在打开事务之前执行；不得只依赖 CLI。成功校验后把同一份已解析对象及计划值传入创建，避免再次读取已变化的文件或以不同默认值生成计划。底层创建接口不提供无确认参数的旁路；可信调用方仍可能自行计算哈希，因此不宣称能防伪确认。

同一 `run_id`、相同规范化 spec 和确认范围的合法重试返回既有 run，不产生第二个批次、不覆盖首次记录或重启计时。不同 spec 沿用 `IDEMPOTENCY_CONFLICT`；同一 spec 但确认范围与已保存记录不同也返回冲突，不能悄悄修改。对没有新记录的旧 run，读取和续跑不需要确认；新版本下对旧 run 重放创建必须提供有效哈希，且只能在 spec 相同且初始固定计划可核对一致时返回原 run，否则返回明确冲突并提示使用 `status`；不得伪造历史确认记录。并发创建由现有锁/事务保证。

### 4.3 记录与时间

`run.plan.segment_brief` 保存 `{brief_version, spec_hash, confirm_hash, confirmation_recorded_at}`，只写入提交并校验成功的记录；时间由创建命令实际时间生成，表示记录时间而非用户确认时间。`status` 返回 plan，可在其中核对，不另假设存在独立的 `plan` CLI 命令。保存完整确认范围所需的初始固定计划值；不能仅依赖后续会被修改的 `plan.research`。不保存轮次、草稿、用户原话或身份，不声称能独立证明谁确认。旧 run 没有此字段时显示「历史批次，无确认记录」。

创建时确认的初始研究时限属于确认范围；后续用户明确要求延长时，沿用 `extend-research` 的现有授权、上限与审计记录，不要求重新确认整个客群。延长不改原始确认记录和哈希；状态同时展示初始与当前时限。其余 `process --resume`、`status --action resume`、`supplement`、`reassess`、`append`、`advance`、`finish`、`export`、`live` 不要求重新确认。v1 新建同样走确认流程。

### 4.4 隐私与状态恢复

业务库保存既有冻结 spec、计划和上述最小记录；不新增草稿分析、字段来源映射、用户原话或客户名单内容。此限制不删除或改变现有业务数据及审计记录。摘要不得泄露客户名单中的具体企业、联系人、邮箱和电话；客户文件摘要只展示数量与文件哈希，不能保证低熵内容的哈希无法被猜测。临时 spec 文件遵循现有本地文件权限和清理策略，不把名单内容复制到临时文件或日志。会话和本地临时文件不等于业务库；无法可靠恢复当前摘要和确认上下文时重新展示并确认。

## 5. 失败与验收

| 编号 | 验收标准 |
|---|---|
| AC-01 | Skill 在展示当前完整摘要后才接受明确确认；展示前「直接跑」、含糊答复、仅提问及确认同时修改配置均不得创建。允许多次修订，每次都重显生效口径并等待确认。通过对话测试覆盖。 |
| AC-02 | CLI 和核心入口均拒绝缺失或不匹配的 `confirm_hash`；在校验失败时确认无数据库连接、准备、维护、网络、run 写入和计时。测试必须覆盖真实包装入口而非仅测试内部函数；不宣称该哈希能证明用户身份或确认行为。 |
| AC-03 | 规范化 spec、有效计划、确定性摘要和 `confirm_hash` 一致；各注册字段、嵌套条件、排除、默认值及 v1/v2 生效语义均可见。遗漏映射失败；格式等价输入稳定，改变任一确认范围有效值使旧哈希失效。检查冻结 spec、初始计划与摘要逐项一致。 |
| AC-04 | `brief` 全链路离线、只读、不启动数据库或维护；稳定测试向量跨进程和重启一致，冲突、限额和未注册字段报告准确。 |
| AC-05 | 同 run 同配置重放、并发创建、不同配置冲突及旧 run 创建重放均按 §4.2 执行；首次记录与计时不被覆盖。数据库测试不得以跳过算通过。 |
| AC-06 | 旧批次可读取和续跑；补证、重评、追加、延长、导出、页面不要求重新确认。延长后初始值、当前值和审计记录均可核对。 |
| AC-07 | 不输出客户名单具体内容；未接入的文件排除明确提示未生效；不将字段来源、草稿或用户原话写入业务库。动态全局抑制名单的适用范围及可变性明确展示。 |
| AC-08 | 行业、来源、渠道及可得性结论可追溯或明确标为未知；来源标签依据可恢复的映射而非从最终值猜测。确认摘要不得把建议变成未配置的硬条件。 |
| AC-09 | 同步 `SKILL.md`、`controller.md`、新增 `references/segment-brief.md` 和 `segment-spec.md`；包含确认状态、失败处理、哈希局限、旧批次及全局抑制名单说明。 |
| AC-10 | 至少一次真实对话演练：展示、用户修改、重新展示、用户确认、创建成功，并核对实际冻结内容；记录轮次、耗时与可见结果，不记录客户名单原文。 |
| AC-11 | 使用真实冻结的 2.3.0 发布包，对 2.4.0 创建的批次进行备份环境读取、续跑与必要导出测试，检查新增 plan 字段、版本校验及数据兼容；确认回滚后旧版不能保证新建批次的确认流程。测试失败则阻止发布或提供经验证的回滚方案。 |
| AC-12 | 展示前可选的取证诊断和离线 `brief` 明确分离；摘要准确显示已测能力、样本规模、时间及未知限制。搜索不可用、域名阻断及 JS 空正文不会被表述为市场没有候选。 |
| AC-13 | 国家规则修复作为独立能力验收：包含 `USA`、`U.S.`、`U.S.A.`、地址上下文、主体不符、目的地、否定/历史表述、裸 `CA` 和代词 `us` 等正反例；分别验证经营地、总部、注册地，并检查原始证据可追溯及未知/冲突状态。修复未交付前不得标为已通过。 |
| AC-14 | 渲染与来源退路作为独立能力验收：覆盖可读静态页、JS 页面、403/429、超时、网络阻断、搜索失效及无法访问的情况；验证限额、记录、检查点、待核状态和不绕过访问限制。能力未交付时展示限制，不得声称已解决。 |
| AC-15 | 在代表性真实任务样本上记录各阶段漏斗、失败原因、耗时与合格吞吐，人工抽检证据准确性，并与相同样本及条件下的基线比较；记录样本量和环境，不以合格数量上升单独证明质量提升。旧批次规则版本和历史计数保持原语义。 |

## 6. 实施与发布顺序

1. 明确规范化、固定计划默认值、摘要字段映射、哈希版本与测试向量；保留原 `spec_hash` 及既有行为。
2. 实现纯预检与 `brief`；调整 CLI 和核心创建入口，在所有副作用前校验，并实现计划记录、幂等及旧批次兼容。
3. 更新 Skill 的展示、澄清、确认与恢复规则和命令文档；明确直接调用核心的信任边界。
4. 为 §3.4 的国家取证、渲染、发现退路及可观测性制定独立实现范围、规则版本和验收；优先复现国家识别问题并量化实际瓶颈。未完成的能力作为限制向用户披露，不能声称确认流程已修复吞吐。
5. 跑自动测试及真实对话演练，完成隔离环境回滚测试。确认流程的 AC-01 至 AC-12 及其实际范围内的规则和能力验收通过后方可发布；AC-13 至 AC-15 在相应取证能力交付时是发布门槛，未交付则明确标记未完成。全部适用项通过并完成实际发布后，统一升 2.4.0、重冻发布、更新安装记录；保留已验证的 2.3.0 回滚点。回滚后若仍要保证新批次必须确认，需要单独限制旧版创建或恢复新版，不能仅依赖旧版 Skill。

本文件为待实施的规格，不代表命令、确认机制或测试已经存在。
